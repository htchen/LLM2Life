## 🧠 洞見段落：讀 `insights.md`，不要只看投影片

四段標 🧠 的內容，**投影片上只有結論，理由在
[`instructor/insights.md`](insights.md)**。那份檔案有完整講稿、每個主張為什麼成立、
以及會被挑戰時怎麼回。上台前務必讀熟——這類主張一定會被問。

**編排原則：先體驗，再命名。** 每個洞見都只講學員十分鐘前剛親身經歷過的事。
非程式背景的聽眾沒有背景知識消化抽象主張，但他們對自己剛剛的感受有絕對的權威。
**順序倒過來就毀了**——把這些搬到開場當「理念說明」，會變成聽不懂的空話。

洞見段落是**唯一不該為了追進度而砍掉的東西**。砍掉它們，這堂課就只剩下
Claude Code 的操作說明書。真的來不及，寧可砍 Lab 3 的首頁步驟（見下）。

## 0:00–0:10 開場 + 現場 Demo

**不要自我介紹超過 60 秒。** 第一件事就是 Demo。

現場打開 Claude Code，用一句話做出一個真的能動的東西。建議題目（跟三個 Lab 都不重疊，
才不會爆雷）：

```text
做一個網頁，我輸入生日，它算出我活了幾天、下一個「整千天」是哪一天，
畫面要好看，直接開一個檔案就能用。
```

做完當場打開來用。然後說一句話收尾：

> 「這個過程我沒有寫任何一行程式。接下來三個小時，你會做三個這樣的東西，
> 而且最後一個全世界都打得開。」

**看什麼：** 這一段的目的是讓「我也做得到」這件事變得可信。不要解釋原理，等下一段。

**落後時：** 不能砍。這是整場的鉤子。

---

## 0:10–0:20 觀念：三個名詞

只講三個詞，每個講到「生活比喻」為止就好，不要展開：

1. **Claude Code** — 一個看得到你電腦裡檔案、而且會自己動手改的助理。
   比喻：不是「問了它給你答案」，是「你交代，它去做，做完給你看」。
2. **Repo（儲存庫）** — 一個會記得所有版本的資料夾。
   比喻：Google Docs 的版本紀錄，但是給整個資料夾用的。
3. **GitHub** — 放 repo 的地方，順便幫你把網頁公開、還能幫你按時做事。
   比喻：雲端硬碟 + 自動化助理。

**一定要講的一件事：** 「Claude 會問你可不可以改檔案，你要按同意。它不會偷偷改。」
非程式背景的人對「AI 動我的電腦」有真實的不安，先講掉。

**看什麼：** 問「有人用過 GitHub 嗎？」舉手數決定 Lab 0 要講多細。

**落後時：** 砍到 6 分鐘，只留 Claude Code 和 GitHub 兩個詞，Repo 在 Lab 0 邊做邊講。
觀念這段已經從 15 分鐘壓到 10——洞見段落會接手大部分的概念工作，這裡不用講滿。

---

## 0:20–0:40 Lab 0：環境 + 建 repo

→ `workbook/lab-0-setup.md`

這是**整場最容易崩的 20 分鐘**。學員理論上在課前已經裝好（見 `pre-workshop-email.md`），
但實際上永遠會有人沒裝。

**開場先做這件事：** 請所有人打開 Claude 桌面版，點 **Code** 分頁。
然後問：「有誰點下去看到要你升級付費方案的？」——請這些人**立刻**舉手，
直接走救援路線，不要讓他們自己卡 15 分鐘。

**三條路線，按順序：**

| 狀況 | 走哪條 |
| --- | --- |
| 桌面版能開 Code 分頁 | 正常路線 |
| 裝不起來 / 公司電腦有限制 | `claude.ai/code`（只要瀏覽器） |
| 沒有付費方案 | 兩人一組，共用一台 |

**兩人一組是正式方案，不是安慰獎。** 直接說「請找旁邊的人一起，一台電腦兩個人做，
負責打字的人輪流」，比讓人單獨枯坐好得多。

**看什麼：** 走動。看螢幕，不要問「大家好了嗎」——沒人會承認自己卡住。
看到有人螢幕停在同一畫面超過 2 分鐘就過去。

**落後時：** repo 的 README 可以不寫，但 **repo 一定要是 Public**，否則 Lab 3 上不了線。

---

## 0:40–1:13 Lab 1：記帳小工具

→ `workbook/lab-1-expenses.md`

第一次真的自己動手。重點不是記帳，是**體驗「講一句話 → 東西出現」**。

**節奏：**

- 0:40–0:45 講「怎麼跟它講話」：講清楚你要什麼、要能看到什麼。給一個爛例子和一個好例子。
- 0:45–1:00 學員貼第一個提示詞，做出 v1，打開來用。
- 1:00–1:09 **改一個東西**（加分類、加刪除、改顏色，隨便）。這一步比 v1 重要——
  它證明「做壞了可以再叫它改」，這是整場最想種下的觀念。
- 1:09–1:13 commit + push，到 GitHub 網頁上看到自己的檔案。

> ⚠️ 「改一個東西」那一步是**洞見 1 的燃料**。學員沒有親手改過，
> 三分鐘後那段「你是在修正自己」就沒有東西可以指。趕時間也要留住這一步。

**一定要講的一件事：** 「不滿意就再講一次，不用重來。」
非程式背景的人會以為講錯一次就毀了，會不敢按 Enter。

**看什麼：** 有人會盯著 Claude 跑而不敢動。走過去說「它在做事，你可以先想下一個要加什麼功能」。

**落後時：** 砍掉 push 到 GitHub，留到 Lab 2 開頭補。做出來能用最重要。

---

## 1:13–1:16 🧠 洞見 1：你剛剛做的不是寫程式，是「說清楚」

→ 講稿：[`insights.md`](insights.md#洞見-1--你剛剛做的不是寫程式是說清楚) · 投影片 33–36

**開場就問全場：「剛剛你改了幾次？兩次？三次？」** 等他們真的回答再翻頁——
這個洞見要成立，得先讓他們承認自己改過。

核心是一句話：那幾次不是在修正 Claude，**是在修正你自己**。
第一次講不清楚，是因為腦袋裡有一整套「還用說嗎」的預設沒講出來。

收在：**你沒辦法把「自己還沒想清楚的事」外包出去。**

**看什麼：** 這段講完會有人露出「原來如此」的表情，也會有人一臉茫然。
不要停下來解釋，直接進休息——休息時間會有人來問，那才是好時機。

**落後時：** 三分鐘壓成一分鐘，只講「那幾次是在修正你自己」和最後那句。
**不要整段砍掉。**

---

## 1:16–1:26 休息

**休息前把下一段的鉤子講掉**，這樣休息回來不用暖機：

> 「剛剛那個東西，要你自己打開才會動。等一下我們要做一個**你不在電腦前面，
> 它自己會做事**的東西。」

休息時間走動處理落後的人。這 10 分鐘是唯一的緩衝。

## 1:26–2:00 Lab 2：每天自動幫你做事

→ `workbook/lab-2-digest.md`

**這一段是全場最有記憶點的。** 學員第一次看到「電腦在別的地方、按時間自己幫我做事」。

**節奏：**

- 1:26–1:31 講 GitHub Actions 是什麼：「GitHub 幫你養的一台電腦，你叫它幾點做事它就做。」
- 1:31–1:46 學員貼提示詞，做出 workflow。
- 1:46–1:54 **手動觸發跑一次**（Actions 分頁 → Run workflow）。這是高潮，留足時間。
- 1:54–2:00 回 repo 看新出現的 `digest/2026-xx-xx.md`。

**技術上最容易爆的三個點（先講，不要等他們踩）：**

1. workflow 必須有 `workflow_dispatch`，否則沒有手動執行的按鈕，現場沒東西可看。
2. workflow 必須有 `permissions: contents: write`，否則它寫得出檔案但推不回 repo，
   會在最後一步紅字失敗。
3. **workflow 檔案要先 push 上去，Actions 分頁才看得到它。** 一定會有人在本機找按鈕。

`instructor/reference/digest-workflow.yml` 是可用的參考解，救人用。

**看什麼：** Actions 跑失敗會是紅色 ✗。紅色不是災難，是好教材——
當場把錯誤訊息貼回 Claude Code 說「修好它」，這一招值得全場看一次。

**落後時：** 砍掉「改成自己想要的來源」那一步，用預設的 RSS 就好。

---

## 2:00–2:03 🧠 洞見 2：值得自動化的門檻，剛剛降到你腳邊

→ 講稿：[`insights.md`](insights.md#洞見-2--值得自動化的門檻剛剛降到你腳邊) · 投影片 51–55

**趁 Lab 2 的情緒高點立刻講，不要等。** 他們剛看到一台不屬於自己的電腦幫自己做事。

論證是一道算術：每週 5 分鐘的麻煩，對上兩個禮拜加一筆錢的開發成本——
**不是不能解決，是不值得解決**。剛剛那 20 分鐘把成本那一邊換掉了，答案整批翻面。

收在：**沒有人會為你一個人寫軟體。以前沒有，以後也不會。但現在你可以。**

**一定要補的一句：** 「那不就一堆爛軟體？」——對，而且沒關係，
使用者只有一個人，就是作者本人。**但拿去給別人用、碰到錢或個資，是完全不同的標準。**
這句不講，等於在鼓勵他們拿玩具去做要緊的事。

**落後時：** 只講算術那張和最後那句，40 秒可以講完。

## 2:03–2:36 Lab 3：習慣儀表板 + 上線

→ `workbook/lab-3-habits.md`

**結尾要給一個真的網址。** 這是他們回家會給別人看的東西。

**節奏：**

- 2:03–2:18 做習慣追蹤頁面。
- 2:18–2:25 做首頁 `index.html`，把三個工具串起來。
- 2:25–2:36 **開 GitHub Pages**，拿到網址，用手機打開。

**手機那一步不要省。** 在自己手機上打開自己做的網站，是這三小時的情緒高點。

**技術上最容易爆的兩個點：**

1. repo 必須是 **Public**（免費帳號）。Lab 0 應該已經處理掉了，這裡再確認一次。
2. Pages 第一次部署要等 1–10 分鐘，而且**剛開好時會是 404**。
   先講，否則整排學員會以為自己做錯了。趁等待時間開始下一段。

**看什麼：** 網址格式是 `https://<帳號>.github.io/my-life-tools/`。
少了最後那個 `/` 或打錯帳號大小寫都會 404。

**落後時：** 砍掉首頁 `index.html`，直接開 Pages，網址指到 `/habits/`。

## 2:36–2:39 🧠 洞見 3：你看不懂程式碼，但你必須看得懂「對不對」

→ 講稿：[`insights.md`](insights.md#洞見-3--你看不懂程式碼但你必須看得懂對不對) · 投影片 68–72

他們今天一直在做驗證（每個 ✅ 檢查點、紅色 ✗、404），只是沒發現。這段幫它取名字。

核心：危險的不是它寫出爛東西——爛東西一眼就看得出來。
**危險的是「看起來很對、但其實不對」，而且它會非常有自信地做錯。**

收在一個帶得走的判準：**越難收回的事，越要親眼看過再放行。**
改顏色讓它做；刪資料、寄信、花錢，先看過。（呼應他們一直在按的「同意」。）

**落後時：** 只講「看起來對 ≠ 對」和那條判準，30 秒。

## 2:44–2:56 🧠 收束論證：今天真正發生的事

→ 講稿：[`insights.md`](insights.md#收束論證12-分鐘) · 投影片 74–88

**全場唯一一段「你在講、而他們願意聽」的時刻**——因為他們手上已經有三個做出來的東西，
你講的每一句都有實體對照。

六段結構，時間分配：

| | 段落 | 分鐘 |
| --- | --- | --- |
| 一 | 今天真正發生的事（兩件同時成立的事） | 1 |
| 二 | **被移走的是哪一塊**（三件事的框架） | 4 |
| 三 | 所以什麼變了（清單變長，長出來的是一人份） | 3 |
| 四 | **誠實的那一半**（四個限制） | 3 |
| 五 + 六 | 該練什麼 + 收束 | 1 |

**第二段是全場的軸心：** 做軟體一直需要三件事——知道要什麼／翻成機器聽得懂的話／
確認它真的對。過去第二件貴到讓另外兩件顯得不重要，貴到我們把整件事叫「寫程式」。
今天第二件幾乎免費了，**剩下的第一件和第三件從來就不是程式能力**。
講到這裡要**刻意放慢**，讓它落地。

**第四段絕對不能省。** 沒有它，前面就是推銷；而且省掉它，第一次踩坑的學員會覺得被騙。

**落後時：** 砍第三段，四段壓成兩分鐘（只講「它會有自信地做錯」和「責任不會轉移」）。
**第二段和第四段不能砍。**

## 2:56–3:00 收尾

投影片 89–95，快速帶過：

1. 三個回家會遇到的坑（一張表，2 分鐘以內，細節在隨堂網站）
2. 五句救命的話

> 「你今天沒有學會寫程式。你學會的是**把想法講清楚**和**確認它真的對**。
> 而這兩件事，本來就是你的。
> 以前它們被埋在『寫程式』底下看不見，今天露出來了。」
