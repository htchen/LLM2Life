## 0:00–0:10 開場 + 現場 Demo

**不要自我介紹超過 60 秒。** 第一件事就是 Demo。

現場打開 Claude Code，用一句話做出一個可以實際操作的工具。建議題目（跟三個 Lab 都不重疊，
以免提前透露後續內容）：

```text
做一個網頁，我輸入生日，它算出我活了幾天、下一個「整千天」是哪一天，
畫面要好看，直接開一個檔案就能用。
```

做完當場打開來用。然後說一句話收尾：

> 「這個過程我沒有寫任何一行程式。接下來三個小時，你會做三個這樣的東西，
> 而且最後一個會發布成公開網站。」

**觀察重點：** 這一段用來展示完整流程。先不解釋原理，下一段再說明名詞。

**進度落後時：** 保留這段，但可縮短展示時間。

## 0:10–0:20 觀念：三個名詞

只講三個詞，每個講到「生活比喻」為止就好，不要展開：

1. **Claude Code** — 可以讀取並修改指定專案檔案的工具。
   與一般聊天介面的差別是：它可以在取得同意後直接執行檔案操作。
2. **Repo（儲存庫）** — 一個會記得所有版本的資料夾。
   比喻：Google Docs 的版本紀錄，但是給整個資料夾用的。
3. **GitHub** — 儲存 repo 的服務，也能發布網頁及執行排程工作。
   可暫時理解為支援版本紀錄與自動化的雲端空間。

**一定要講的一件事：** 「Claude 會問你可不可以改檔案，你要按同意。它不會偷偷改。」
先說明每次修改都需要使用者確認，降低學員對檔案被更動的疑慮。

**觀察重點：** 問「有人用過 GitHub 嗎？」依舉手人數決定 Lab 0 的說明深度。

**進度落後時：** 縮短至 6 分鐘，只留 Claude Code 和 GitHub；Repo 在 Lab 0 操作時說明。
觀念這段已經從 15 分鐘壓到 10——洞見段落會接手大部分的概念工作，這裡不用講滿。

## 0:20–0:40 Lab 0：環境 + 建 repo

→ `workbook/lab-0-setup.md`

這是**整場最容易出問題的 20 分鐘**。學員理論上在課前已經裝好（見 `pre-workshop-email.md`），
現場仍可能有人尚未完成安裝。

**開場先做這件事：** 請所有人打開 Claude 桌面版，點 **Code** 分頁。
然後問：「有誰點下去看到要你升級付費方案的？」請這些人立即舉手，
改用備用方案，避免等待過久。

**三條路線，按順序：**

| 狀況 | 走哪條 |
| --- | --- |
| 桌面版能開 Code 分頁 | 正常路線 |
| 裝不起來 / 公司電腦有限制 | `claude.ai/code`（只要瀏覽器） |
| 沒有付費方案 | 兩人一組，共用一台 |

**兩人一組是正式備用方案。** 直接說：「請找旁邊的人一起，一台電腦兩個人操作，
並輪流負責輸入。」

**觀察重點：** 走動查看螢幕，不只詢問「大家好了嗎」。
看到有人螢幕停在同一畫面超過 2 分鐘就過去。

**進度落後時：** 可省略 repo 的 README，但 repo 必須設為 **Public**，否則 Lab 3 無法發布。

## 0:40–1:13 Lab 1：記帳小工具

→ `workbook/lab-1-expenses.md`

這是第一次由學員自行操作。重點是體驗「描述需求 → 產生結果 → 實際驗證」。

**節奏：**

- 0:40–0:45 說明提示詞：寫清楚需求與可觀察的結果，並比較資訊不足與資訊完整的例子。
- 0:45–0:58 學員貼第一個提示詞，做出 v1，打開來用；確認能動後先 commit，留下安全存檔點。
- 0:58–1:08 **改一個東西**（加分類、加刪除、改顏色，隨便），再親手測一次。這一步比 v1
  重要，因為學員會練習修改、驗證及必要時還原。
- 1:08–1:13 把第二塊另做一次 commit + push；到 GitHub 點進最新 commit，確認改動都跟新功能有關。

**在這裡說明操作節奏：**「做一小部分 → 打開查看 → 親手測試 → commit 保留版本」。不用教
block/module 專有名詞，也不用拆成很多檔案；重點是範圍小到學員自己能驗收、壞了能退回。

> ⚠️ 「改一個東西」是洞見 1 的必要經驗。學員需要先經歷補充需求的過程，
> 才能理解需求會在修改中逐步釐清。時間不足時仍應保留這一步。

**一定要講的一件事：** 「需要調整時，直接補充需求，不用重來。」
說明提示詞可以持續補充，修改失敗也可以還原，讓學員理解不必一次寫完所有需求。

**觀察重點：** 工具執行期間，可提醒學員先準備下一項修改需求。

**進度落後時：** 可將 push 延到 Lab 2 開頭補做，先完成可操作版本。

## 1:13–1:16 🧠 洞見 1：尚未釐清的需求無法完整交給 AI

→ 講稿：[`insights.md`](insights.md#洞見-1--尚未釐清的需求無法完整交給-ai) · 投影片 33–36

**開場就問全場：「剛剛你改了幾次？兩次？三次？」** 等他們真的回答再翻頁——
先取得幾個實際回答，再說明修改次數與需求釐清的關係。

核心是一句話：每次補充條件，都是在把原本隱含的需求說明得更完整。
第一次提示詞通常不會包含所有條件，看到結果後才會注意到缺少哪些限制。

收在：**尚未釐清的需求，無法完整交給人或 AI 執行。**

**觀察重點：** 若學員對抽象說法沒有反應，可用剛才的中文介面、刪除功能或手機版面為例；
說明一個例子後進入休息，個別問題可在休息時間處理。

**進度落後時：** 縮短為一分鐘，只保留「補充條件是在釐清需求」及最後一句結論。

## 1:26–2:00 Lab 2：每天自動幫你做事

→ `workbook/lab-2-digest.md`

這一段讓學員第一次實際看到雲端排程工作。

**節奏：**

- 1:26–1:31 說明 GitHub Actions：GitHub 依照 workflow 在雲端執行指定工作。
- 1:31–1:46 學員貼提示詞，做出 workflow。
- 1:46–1:54 **手動觸發執行一次**（Actions 分頁 → Run workflow），並保留足夠時間觀察結果。
- 1:54–2:00 回 repo 看新出現的 `digest/2026-xx-xx.md`。

**三個常見技術問題（操作前先說明）：**

1. workflow 必須有 `workflow_dispatch`，否則不會顯示手動執行按鈕，也無法在課堂上示範結果。
2. workflow 必須有 `permissions: contents: write`，否則它寫得出檔案但推不回 repo，
   會在最後一步紅字失敗。
3. **workflow 檔案要先 push 上去，Actions 分頁才看得到它。** 一定會有人在本機找按鈕。

`instructor/reference/digest-workflow.yml` 是可用的參考解，救人用。

**觀察重點：** Actions 執行失敗會顯示紅色 ✗。可示範複製完整錯誤訊息，
貼回 Claude Code 並請它分析及修改。

**進度落後時：** 省略「改成自己想要的來源」，使用預設 RSS。

## 2:00–2:03 🧠 洞見 2：自動化的成本已明顯降低

→ 講稿：[`insights.md`](insights.md#洞見-2--自動化的成本已明顯降低) · 投影片 51–55

Lab 2 完成後立即說明，讓學員以剛才的雲端執行結果作為對照。

論證以成本比較為主：若每週手動處理只需 5 分鐘，而製作工具需要數週與額外費用，
通常不值得開發。當製作時間縮短到約二十分鐘，更多個人需求會進入可行範圍。

收在：**只供自己使用的工具，也可能值得製作。**

**必須補充：** 個人使用的低風險工具可以採較簡化的標準；提供他人使用、涉及金錢或個人資料時，
需要增加安全、測試與維護措施。

**進度落後時：** 只保留成本比較及最後一句，約 40 秒。

## 2:03–2:36 Lab 3：習慣儀表板 + 發布成公開網站

→ `workbook/lab-3-habits.md`

結尾要取得一個可公開開啟的網址，作為發布成果。

**節奏：**

- 2:03–2:18 做習慣追蹤頁面。
- 2:18–2:25 做首頁 `index.html`，把三個工具串起來。
- 2:25–2:36 **開 GitHub Pages**，拿到網址，用手機打開。

**保留手機開啟步驟。** 這一步可以驗證網站是否真的能由其他裝置存取。

**兩個常見技術問題：**

1. repo 必須是 **Public**（免費帳號）。Lab 0 應該已經處理掉了，這裡再確認一次。
2. Pages 第一次部署要等 1–10 分鐘，而且**剛開好時會是 404**。
   先講，否則整排學員會以為自己做錯了。趁等待時間開始下一段。

**觀察重點：** 網址格式是 `https://<帳號>.github.io/my-life-tools/`。
少了最後那個 `/` 或打錯帳號大小寫都會 404。

**進度落後時：** 省略首頁 `index.html`，直接開啟 Pages，網址指到 `/habits/`。

## 2:36–2:39 🧠 洞見 3：不必讀懂全部程式碼，但必須驗證結果

→ 講稿：[`insights.md`](insights.md#洞見-3--不必讀懂全部程式碼但必須驗證結果) · 投影片 68–72

學員已經透過每個 ✅ 檢查點、紅色 ✗ 與 404 練習驗證；這段說明這些操作的共同目的。

核心：明顯不符合需求的結果容易發現；更需要注意的是外觀看似正確、實際行為卻不正確的結果。
AI 的語氣可能很確定，但輸出仍需要驗證。

收在一個帶得走的判準：**越難收回的事，越要親眼看過再放行。**
改顏色讓它做；刪資料、寄信、花錢，先看過。（呼應他們一直在按的「同意」。）

**進度落後時：** 只講「看起來正確不等於已通過驗證」和那條判準，約 30 秒。

## 2:44–2:56 🧠 收束論證：今天真正發生的事

→ 講稿：[`insights.md`](insights.md#收束論證12-分鐘) · 投影片 74–88

學員已完成三個成果，因此這一段應逐項連結到實際操作，不另加抽象概念。

六段結構，時間分配：

| | 段落 | 分鐘 |
| --- | --- | --- |
| 一 | 今天真正發生的事（兩件同時成立的事） | 1 |
| 二 | **被移走的是哪一塊**（三件事的框架） | 4 |
| 三 | 所以什麼變了（清單變長，長出來的是一人份） | 3 |
| 四 | **使用限制**（四個限制） | 3 |
| 五 + 六 | 該練什麼 + 收束 | 1 |

**第二段是核心：** 做軟體需要三件事——知道要什麼、翻成機器可以執行的形式、
確認結果正確。生成工具降低了第二項工作的部分成本，因此需求釐清與驗證會占更高比例。
講到這裡應放慢速度，並對照三個 Lab 的例子。

**第四段不能省略。** 這一段說明工具限制、風險差異與使用者責任，讓學員知道課堂成果的適用範圍。

**進度落後時：** 省略第三段，第四段縮短為兩分鐘，只保留「輸出仍可能有錯」和「責任不會轉移」。
第二段和第四段必須保留。
