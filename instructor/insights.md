# 開放式專題：講師說明與帶領原則

這份文件說明課程各階段的教學目的、講師提問方式與常見範圍問題。

## 核心主張

課程不以完成三個固定工具為目標，而是讓學員走完一次可重複的專題流程：

> **提出問題 → 定義目標 → 拆解計畫 → 分段實作 → 驗證 → 決定下一步**

固定案例只建立共同操作基礎。學員的個人專題需要來自熟悉的教學情境，
因為使用者本人最能判斷問題是否真實、結果是否符合需求。

---

## 一、共同練習之後：需求會在看到結果後變得更明確

請學員回答：「看到第一版後，你才發現哪一項需求沒有寫？」

第一版不是最終答案，而是用來取得具體回饋。學員修改探究提問卡時，實際經歷了：

1. 先提出目前理解的需求
2. 看見可操作結果
3. 發現隱含條件
4. 更新需求並再次驗證

收在：

> **尚未釐清的需求，無法完整交給人或 AI 執行。**

這也是後續專題允許修改計畫的原因。計畫是目前的最佳理解，不是不能改動的規則。

## 補充段落：AI 演進與人的判斷（1:03–1:15）

這一段接在回顧之後、休息之前，投影片 29–40。目的是在學員開始自己的專題之前，
先給他們一組判斷依據：**哪些事情可以放心交給工具，哪些必須自己承擔。**
沒有這一段，實作階段的取捨只能靠個別學員的直覺。

投影片只放結論。以下是結論背後的推導、講法與追問回應。

### 推導順序（不可調換）

```text
被記錄下來的文明 → 程式可以自主閉環 → 物理世界會斷環 → context 造成差異
→ 還要不要學程式 → 資訊系該學什麼 → 人的價值
```

三個問題的答案都是前四個觀點的推論。若先講問題再補觀點，聽起來會像個人立場，
而不是可以檢驗的推理。

### 觀點一：它濃縮的是已經被記錄下來的文明

模型的材料是人類留下的文字、程式碼、影像與聲音。因此它的能力分布並不平均，
而是貼著人類的紀錄密度：紀錄愈密的領域愈強，沒有被寫下來的部分它沒有來源。

**講法：** 它讀過的是人類的紀錄，不是你的處境。

**現場可用的對照：** 提問卡第一版做得很快，因為表單與清單這種結構被寫過無數次；
但「你為什麼要分這幾個類別」沒有人替你寫過，所以那一段永遠要你補。

### 觀點二：程式領域可以自主閉環

電腦、網路與程式本身就是一個可以完全自主互動的環境。模型能產生程式、實際執行、
讀到結果、再自己修正，整個迴圈不需要人介入。加上這個領域的紀錄最完整、最公開，
兩個條件同時成立，所以進步最快。

**講法：** 它強在寫程式，不是因為程式比較簡單，是因為程式的對錯它自己看得到。

**可以回頭指的證據：** 開場 Demo 時它自己打開網頁確認結果，那一步就是閉環。

### 觀點三：牽涉到物理世界，迴圈就會斷

它無法自己到現場、量測、試用、承擔。提出做法之後，執行與觀察兩步只能由人接上，
回饋才回得去。斷環的代價是速度：程式的錯誤幾秒鐘就知道，教學的成效
可能要一個學期才知道。

**收在：** 迴圈愈慢，人的判斷佔的比重就愈高。

**注意：** 不要說成「AI 碰不到現實」。感測器與機器人正在補這一段。
真正穩定的分界不是「能不能碰」，而是**錯了誰承擔、多久才知道**。

### 觀點四：差異來自 context

兩個人的差別，多半不在會不會，而在各自累積了什麼經驗與記憶。模型帶著的是人類共同的紀錄，
每次對話重新開始，沒有立場，也不承擔結果；你帶著的是只有你在場才知道的事、
連續累積會被修正的經驗、明確的取捨，以及後果。

**講法：** 同一個工具，不同的人用出不同的結果。差別在你給了它什麼脈絡。

**接回課程：** 回顧時寫下的那一項「沒說出口的需求」，就是在補 context。
專題簡述、「這次不做」與驗收條件，都是把 context 寫成可以交出去的形式。

### 主張

> 能自主驗證的事，會愈來愈快；不能自主驗證的事，仍然靠人。

產生的門檻在下降，判斷與脈絡的門檻在上升。兩件事同時發生，
所以「不用學了」和「照原來的方式學」都不夠準確。

時間不足時其他張可以略過，這一張不要略過。

#### 從描述推到策略

主張本身是描述性的。被問到「那實際上該怎麼做」時，把它翻成祈使句：

> **所以要設法把事情變成能自主驗證的。**

具體做法是**先建能自動判斷對錯的裝置，再讓各種方案在上面競爭**——
測試環境、benchmark、可重複執行的檢查。這正是善用模型最強的那項能力：
它可以自己執行、自己讀結果、自己修正，所以先讓它把「驗證的裝置」蓋出來，
之後每一個想法都有地方可以被檢驗，包括你自己的創新想法。

這也是問題二「需要補上」列在最前面的那一項。

**但有兩個反面必須一起講，否則會教出錯的東西。**

**一、benchmark 一旦存在，就會變成目標。** 方案會朝著指標最佳化，
而不是朝著真正想要的東西。判斷沒有消失，它搬到了新的位置：
「這個 benchmark 還在衡量我在乎的事嗎？」這在機器學習領域反覆發生，
不是理論上的疑慮。

**二、不是所有事情都能被自動量測，而那條界線正好是觀點三。**
需要人判斷的事，往往就是最抗拒被量測的事。所以這個策略與觀點三互相定義邊界：
**能被自動量測的，就儘量做成閉環；做不到的，那正是人留下來的地方。**

**不要把這一段下放到動手層。** 課堂有一條檢查點是「第一步就要產生可操作的核心流程」。
學員若先花時間蓋測試裝置，三十分鐘後會什麼都展示不出來。
這是講述層的策略，不是三小時場次的實作方法。

**教師可以怎麼轉譯：** 「先訂出怎麼判斷對錯，再去試各種做法」，
在科學課裡就是**操作型定義與實驗設計**——先講清楚要測什麼、怎麼算數，
再開始蒐集資料。學生最常見的失敗不是做錯實驗，而是做完才發現當初沒定義清楚要看什麼。

### 三個問題的回答

**還需不需要學習寫程式？** 要學，但學的層次往上移一層。
以前花最多時間的（記語法、搭樣板、從零實作、讀完文件才動手），正好是模型能自主閉環的部分；
之後值得花時間的是寫出可驗收的規格、判斷產出與風險、控制一次變動的範圍、讀懂錯誤與資料流向。

**資訊工程系該學什麼？** 三層分開講，不要含混成「基礎更重要」：

- 更重要了：系統與資料如何運作、除錯與驗證的方法、安全與邊界條件、把需求轉成規格
- 需要補上：評估 AI 產出的品質、設計驗收與測試、把模型當成系統的一個元件、把真實世界的限制帶進設計
- 會被稀釋：純語法的熟練度、樣板的記憶量、重複性實作的速度

收在：可以少教打字，不能少教判斷。

**人的價值在哪裡？** 四件事目前不會被接手：決定哪一個問題值得處理、決定這次不做什麼、
承擔結果帶來的後果、提供只有你才有的脈絡。收在：模型沒有「想要」，目標一律來自人。

### 這一段不要做的事

- 不比較模型廠牌、不報效能數字、不預測時間點
- 不打字、不示範，這一段是講述段落
- 不說「AI 什麼都不會」，也不說「AI 會取代所有人」；兩種說法都會讓後面的專題失去分寸
- 提問超過 2 分鐘就收回主張並進休息，剩下的追問留到展示階段

### 常見追問

| 追問 | 回應方向 |
| --- | --- |
| 再過幾年它就能自己處理現實世界了吧？ | 部分會。但分界不是「能不能碰」，是錯了誰承擔、多久才知道。回饋愈慢，人的判斷比重愈高。 |
| 它寫的程式可以信嗎？ | 在能自動驗證的範圍內可信度高，而驗證方式是人設計的。今天的驗收條件就是在做這件事。 |
| 記憶變長之後，context 是不是就不重要了？ | 記憶長度不等於承擔。它可以保留你給的紀錄，不會替你經歷，也不會替你負責。 |
| 那還要不要念資訊系？ | 要。重心從產出速度移到驗證、整合與邊界判斷，這些仍然需要系統性的訓練。 |
| 初階工程師會不會被取代？ | 初階工作的定義會改變。缺的不是打字的人，是能判斷產出對不對的人。 |
| 這些說法會不會很快過時？ | 演進的細節會過時。主張的形式比較穩定：能不能自主驗證，決定它走得多快。 |
| 我可以用 Gemini／ChatGPT 嗎？ | 可以，流程完全成立，有些介面產生第一版還更快。不能省的是把成果存回 GitHub——網址、回溯、所有權、交付這四件事，廠商託管的 canvas 目前給不了。詳見種子教師指南。 |

## 二、發想階段：先確認問題，再討論功能

學員常會直接說「我要做一個 App」。講師需要追問：

- 你在什麼情境會用？
- 現在怎麼處理？
- 哪一個步驟造成困難或重複工作？
- 誰會使用？
- 如果只改善一件事，哪一件最重要？

不要在這個階段直接提供功能清單。先讓學員把問題說完整，功能才能對應實際需要。

選題不是比較創意，而是比較哪一題最適合在有限時間內產生可驗證結果。

---

## 三、定義階段：最小版本需要明確的邊界

一頁專題簡述必須包含：使用者、情境、問題、本次目標、必要功能、不做內容、驗收條件。

「這次不做」不是附帶項目，而是範圍管理的核心。若學員無法列出不做內容，通常表示題目仍過大。

適合課堂的題目：

- 一個主要使用者
- 一個核心問題
- 一個可展示流程
- 2–3 項必要功能
- 可用畫面或操作驗證
- 低風險、可回復

不適合直接做為課堂版本：登入、付款、醫療或法律判斷、敏感個資、多人即時同步、
大量外部資料整合、自動對外寄送。

---

## 四、規劃階段：每一步都要能被驗收

不要接受只有技術名稱的計畫，例如「建立前端、處理後端、整合資料庫」。
對初學者有用的計畫需要說明完成後的行為：

> 第一步：可以輸入一筆資料並顯示在畫面上。驗收：輸入範例後，列表出現相同內容。

好的第一步不是空白框架，而是最小但完整的核心流程。後續每一步增加一項能力。

計畫的工作是降低同時變動的範圍，讓問題發生時能判斷是哪一步造成，也能回到上一版。

---

## 五、實作階段：以驗收條件帶動迭代

講師巡視時先問「你這一步的驗收條件是什麼」，不要先看功能數量。

每一輪固定使用：

1. 指定目前步驟
2. 工具執行
3. 打開結果
4. 依驗收條件操作
5. 測試原有核心流程
6. commit 保存版本

若結果讓學員改變需求，先更新簡述或計畫，再修改檔案。這不是偏離流程，而是正常的需求學習。

---

## 六、展示階段：展示判斷，不比較完成度

每位學員用一分鐘說明：問題、縮小後的目標、成果操作、驗收方式、下一步。

未完成全部功能不等於失敗。若學員有可操作版本、知道哪些條件未通過，並能說明下一步，
就已完成一次完整的專題循環。

不要在分享階段比較功能數量或視覺效果。重點是題目與結果之間是否一致。

---

## 收束說法

> 今天完成的不是一組固定答案，而是一套可以重複使用的工作方式。
>
> AI 可以協助整理、規劃與實作；問題是否值得處理、目標如何取捨、結果是否正確，
> 仍需要由使用者判斷。
>
> 下一次可以從新的問題重新開始，也可以沿用今天的驗收結果規劃下一版。

## 常見問題

| 問題 | 回應方向 |
| --- | --- |
| 題目差異太大，講師怎麼支援？ | 固定流程與技術範圍，不固定題目。先檢查是否為單一網頁、單一流程與低風險需求。 |
| 學員一直增加功能？ | 回到三項必要功能與「這次不做」。新增內容先放入下一版。 |
| 第一輪仍沒有可操作結果？ | 縮小第一步，只保留輸入與一個可見輸出。 |
| AI 建議的計畫不合理？ | 學員可修改或拒絕。計畫需要符合使用情境與驗收方式。 |
| 沒有完成公開網站？ | 先展示本機版本。發布是傳遞成果的方式，不是判斷專題是否完成的唯一標準。 |
