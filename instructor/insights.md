# 洞見段落：講稿與論證（講師用）

這份檔案整理各段主張、理由與 Q&A 回應。投影片只呈現摘要，講師應在課前讀完本文件。

三個微段落各 3 分鐘，放在對應的 Lab 之後；最後一個 12 分鐘的收束論證。

**編排原則：先體驗，再命名。** 每個洞見都只講**他們十分鐘前剛親身經歷過的事**。
非程式背景的聽眾較難在沒有實例時理解抽象主張，因此先讓學員操作，再說明操作所反映的原則。

如果把這些內容移到開場，學員尚未有操作經驗可以對照，理解效果會降低。

## 洞見 1 — 尚未釐清的需求無法完整交給 AI

**位置：** Lab 1 之後，休息之前 · **3 分鐘**

### 他們剛經歷了什麼

第一版可能未完全符合需求。學員補充條件後，工具逐步接近預期結果。
這段要指出：修改過程同時也是釐清需求的過程。

### 怎麼講

> 剛剛你修改了幾次？每次補充了哪些條件？
>
> 第一次的提示詞通常沒有包含所有條件。看到第一版之後，你才會注意到還需要中文介面、
> 刪除功能、手機版面或更清楚的金額格式。
>
> 這些條件對你而言可能理所當然，但 AI 不會知道沒有寫出的需求。
>
> Claude Code 降低了把需求轉成程式碼的成本，但需求本身仍需要由使用者釐清。

**收在這一句上，然後停頓：**

> **尚未釐清的需求，無法完整交給人或 AI 執行。**

### 為什麼這是真的（Q&A 用）

需求沒有說明的條件，不會因為程式碼產生得更快而自動補齊。當程式碼產生速度提高時，
需求釐清、取捨與驗收會占更高比例。

### 會被挑戰的點

- **「所以你是說寫程式沒價值了？」**
  不是。程式架構、取捨、除錯與維護仍需要專業能力；降低的是把明確需求轉成初步程式碼的成本。
- **「那我幹嘛還要學表達？AI 會猜。」**
  AI 可以補足部分資訊，但推測可能與實際需求不同，因此仍需要明確描述與驗證。（接洞見 3）

## 洞見 2 — 自動化的成本已明顯降低

**位置：** Lab 2 之後 · **3 分鐘**

### 他們剛經歷了什麼

學員約用二十分鐘建立一個每天早上六點執行的工作。這時說明成本變化與適用範圍。

### 怎麼講

> 是否值得自動化，可以比較持續手動處理的時間與製作工具的成本。
>
> 如果一件事每週只花 5 分鐘，但製作工具需要數週與額外費用，通常不值得開發，
> 因此會持續以人工處理。
>
> 剛才的練習約用二十分鐘完成。當製作與修改工具所需的時間降低，
> 更多原本不適合自動化的個人需求會進入可行範圍。

**收束：**

> **只供自己使用的工具，也可能值得製作。**

### 為什麼這是真的

商業軟體通常優先處理多人共有的需求，因為開發與維護成本需要由使用者共同分擔。
當個人可以用較少時間製作工具，原本規模太小的需求也可能值得處理。

### 會被挑戰的點

- **「這樣會不會產生很多品質不佳的工具？」**
  有可能。個人使用的工具可以依風險採用較簡化的標準；提供他人使用、涉及金錢或個人資料時，
  則需要增加安全、測試與維護措施。**用途決定所需的嚴謹程度。**
- **「我做的東西會不會壞掉沒人修？」**
  可能需要維護。生成工具可以降低部分修改成本，但使用者仍需保留版本並驗證修改結果。

## 洞見 3 — 不必讀懂全部程式碼，但必須驗證結果

**位置：** Lab 3 之後 · **3 分鐘**

### 他們剛經歷了什麼

紅色的 ✗、404，以及每一段結尾的 ✅ 檢查點，都是驗證活動。

### 怎麼講

> 今天每一段結尾我都放了一個「✅ 檢查點」。
> 這些檢查點是在練習驗證結果。
>
> 明顯不符合需求的結果容易發現；更需要注意的是外觀看似正確、實際行為卻不正確的結果。
> AI 的語氣可能很確定，但輸出仍需要驗證。
>
> 因此，不必把「讀懂全部程式碼」當成第一個目標。先做到：
>
> **在它動手之前，你先說得出「做好了應該長什麼樣」。**
>
> 不要只依據「完成了」這句回覆。**請打開畫面、查看截圖或實際執行一次。**
> 你今天輸入幾筆記帳、按一次 workflow、用手機打開網站，都是 visualization——
> 把抽象的程式變成你親眼能判斷的行為。

**提供一個判斷原則：**

> **越難收回的事，越要親眼看過再放行。**
>
> 調整顏色等可回復的修改，可以先執行再檢查。
> 刪除資料、寄送訊息或產生費用前，應先確認內容與影響。

請學員帶走四個驗收問題，不另開新概念：

1. **能不能重試，或回到上一個 commit？**
2. **做好了，我應該看到什麼？**
3. **錯了誰會看到，影響是什麼？**
4. **有沒有畫面、截圖或實際執行結果可以親眼看？**

（呼應他們今天一直在按的「同意」按鈕，以及 plan 模式。）

### 為什麼這是真的

自動化偏誤（automation bias）會讓人因系統多數時候正確而降低查核頻率。
對非程式背景的使用者而言，實際操作與事先定義驗收條件，是比逐行閱讀程式碼更可行的查核方式。

### 會被挑戰的點

- **「我又看不懂，怎麼驗證？」**
  先驗證**行為**：輸入這個，應該出現那個。請它打開畫面、看截圖、
  實際跑一次；推上 GitHub 後看那次 commit 的 diff，確認改動都跟新功能有關、沒有誤刪其他東西。
  這些都是 visualization，不需要先理解所有程式語法。
- **「那不是很累？」**
  依風險調整驗證程度；越難回復的操作，越需要完整檢查。

## 收束論證（12 分鐘）

**位置：** 洞見 3 之後、成果分享之前

學員已完成三個成果，此時可以用實際操作經驗說明整體框架。

### 一、今天真正發生的事（1 分鐘）

> 這堂課不是程式設計入門，也不以學會程式語法為目標。
>
> 你們完成了三個可使用的工具，其中一個已發布成公開網站。
>
> 同時也練習了：**把模糊的想法拆成小步驟、說明清楚，再實際驗收。**
>
> 接下來用這三項結果說明 Claude Code 改變了哪一部分工作。

### 二、被移走的是哪一塊（4 分鐘）

> 做出一個軟體，從以前到現在都需要三件事：
>
> **一、知道要什麼。**
> **二、把它翻譯成機器聽得懂的話。**
> **三、確認它真的對。**
>
> 過去，第二件事需要較多時間與專業訓練，因此常成為軟體開發的主要門檻。
>
> 今天，Claude Code 可以處理第二件事的大部分初步工作。
>
> 剩下第一件和第三件。

**停頓，然後：**

> 第一件與第三件的核心，是對需求、情境與結果的理解，不以程式語法為前提。

這是整場的核心主張，請放慢速度並用 Lab 例子對照。

### 三、所以什麼變了（3 分鐘）

> 變的不是「工程師會消失」。
>
> 改變的是：製作成本降低後，更多小規模需求值得被處理。
>
> 新增的需求中，有許多是**個人使用**：
> 只有你需要、只有你知道為什麼需要、只有你在乎它對不對。
>
> 過去這類需求通常不會形成商業軟體，現在使用者可以自行製作。

### 四、使用限制（3 分鐘）— **必須保留**

這一段用來說明工具的限制與使用者責任，不應省略。

> 使用 Claude Code 時，需要注意四件事：
>
> **一、AI 的語氣可能很確定，但輸出仍可能有錯。** 看起來正確不等於已通過驗證。
>
> **二、最後一部分通常最花時間。** 課堂題目已控制範圍；自行製作其他工具時，
> 細節可能需要較多修改與測試時間。
>
> **三、責任不會轉移。** 可以把執行工作交給 Claude Code，
> 但規劃、決策與驗收仍由使用者負責。
>
> **四、完成這堂課不等於具備所有軟體開發能力。**
> 本課程練習的是需求描述與驗證，其他能力需要另外學習。

### 五、後續練習重點（1 分鐘）

> 兩件事：
>
> **練習描述需求**——把隱含條件、限制與預期結果寫出來。
>
> **練「驗證」**——動手之前先想「做好了應該長什麼樣」。
>
> 請在自己熟悉的工作領域練習這兩項能力，因為你最了解該領域的需求與判斷標準。

### 六、收束（30 秒）

> 回家作業第三題是「做一個只有你需要的小工具」。
>
> 個人工作流程通常只有本人最了解，因此適合作為後續練習題目。

接原本的結尾投影片。

## Q&A 常見問題

| 問題 | 怎麼回 |
| --- | --- |
| 「工程師會失業嗎？」 | 不預測就業結果。回到課程範圍：初步程式碼產生成本降低，但架構、判斷、驗證與維護仍需要專業能力。 |
| 「這樣做出來的工具能公開發布嗎？」 | 依用途回答。個人使用可採較簡化的標準；提供他人使用、涉及金錢或個人資料時，需要另一套安全與測試要求。 |
| 「我還需要學程式嗎？」 | 依目標回答。個人小工具未必需要先學程式語法；若要建立他人依賴的系統，程式設計與軟體工程能力仍然重要。 |
| 「AI 會不會使用我的資料？」 | 說明本課程工具的資料保存在瀏覽器，但 Claude 服務本身的資料政策應以使用者方案的官方文件為準，不提供文件以外的保證。 |
| 「為什麼我做的跟 Demo 不一樣？」 | 說明 Demo 題目與提示詞事先測試過；結果差異通常來自需求描述、模型輸出與執行環境。 |

### 備用素材（時間有餘、或被問到歷史脈絡時才用）

試算表可作為類比：Excel 讓沒有程式設計職稱的人也能自行處理運算工作。
類似地，生成工具可能讓更多人自行處理原本需要委託開發的個人需求。
