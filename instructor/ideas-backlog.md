## 一、全新 Lab／工具主題構想

### 備用題目池
同樣的技術骨架（本機 localStorage → GitHub Actions 自動化 → GitHub Pages 上線）不變，
換場次/換受眾時抽換題目，比每次改整套教材輕：

| 位置 | 技術骨架不變 | 現有題目 | 備用題目 |
| --- | --- | --- | --- |
| Lab 1（本機、localStorage） | 單檔 HTML，看一句話變一個東西 | 記帳 | 待辦清單、情緒/心情日記、看書清單、水分/服藥提醒卡 |
| Lab 2（自動化、GitHub Actions） | 排程寫檔、手動觸發跑一次 | RSS 每日摘要 | 每日一句英文單字、匯率/天氣快照、紀念日倒數提醒、閱讀進度週報 |
| Lab 3（上線、GitHub Pages） | localStorage + 首頁串接 | 習慣追蹤 | 個人作品集頁、家庭行事曆看板、讀書清單展示頁 |

### 換受眾、不換骨架的變體
仿照 `variant-free/`（換機制、不換論證）的模式，換成換**受眾**：

- **給老師的版本**：Lab 1 → 隨堂測驗小工具，Lab 2 → 每週學生表現摘要，Lab 3 → 班級公告板。
  收束論證「一人份」換成「一班份」；誠實限制段第三點（責任不轉移）碰到學生成績會更有份量。
- **給店家/工作室的版本**：Lab 1 → 訂單/庫存小工具，Lab 2 → 每日營業額摘要，Lab 3 → 店面介紹頁。
  「拿去給別人用是另一套標準」直接對到他們真實會不會碰錢、碰客戶資料的情境。

這兩個都是換題目 + 微調收束論證，成本遠低於再做一個完整分岔（像 `variant-free/` 那樣）。

## 二、洞見／收束論證深化候選

### 洞見 1（你剛剛做的不是寫程式，是「說清楚」）

- **新角度**：Claude 跟新來的助理不一樣——助理聽不懂會反問你，Claude 聽不懂會**直接照
  猜測動手**。可以提前埋洞見 3 的伏筆（它會很有自信地猜錯）。
- **新的 Q&A 反駁**：「那我幹嘛不先想清楚再打字？」——很多時候要先看到一個具體但錯的
  版本，才想得起來自己要什麼（隱性知識靠對照才浮現），比「你就是懶得想」站得住腳。

- **⭐ 使用者 2026-08-26 提出：「有人推廣要用 block/module 形式來使用 Claude Code
  開發程式」——把大要求拆成一塊一塊、一塊一塊驗，可行性高，而且這堂課骨架本身就在做
  這件事，只是沒有明講成一個技巧：**

  - **為什麼可行**：範圍越小，AI 越不用「猜」，出錯率跟著掉（直接對到洞見 1 的核心
    論點）；範圍越小，也越容易驗收（對到洞見 3）。三個 Lab 的每個步驟本來就是
    「做一件事 → ✅ 檢查點」，Lab 2 更明確是三段式（寫 workflow → 手動觸發驗證 →
    看輸出檔案）——**學員今天做的事，就是 block/module 開發，只是沒有名字。**
  - **可以明講成技巧的做法**：① 先讓 Claude Code 列出「這個東西可以拆成哪幾塊」，
    看過拆法再動手，不要一開口就要完整成品；② 一次只做一塊、驗證過再做下一塊，
    不要一個 prompt 要求做完所有功能；③ 每一塊做完就 commit 一次，不要全部做完才
    commit（比現有 Lab 1「做出 v1 → 改一個東西 → commit」的節奏更細）；④ 請 Claude
    Code 用清楚的區塊/註解把功能分開，之後要改就說「改『分類』那一塊」，不用重新描述
    整個畫面——**這個做法不需要多檔案或 build 工具**，跟這堂課「單檔、零安裝」的設計
    限制不衝突。
  - **放的位置建議**：不用另開一段，適合當「回家作業」或「五句救命的話」裡補一句
    可操作的技巧——現有洞見比較偏「為什麼」，這個是「怎麼做」，兩者互補。
  - **要避開的坑**：字面上的 block/module 視覺化拖拉編輯器（像 Scratch）是完全不同的
    東西，Claude Code 本身是文字工具不是積木編輯器，**這堂課不應該往那個方向延伸**，
    會牴觸單檔／零安裝的設計前提。

- **⭐ 使用者 2026-08-25 提出的類比，值得認真評估放進洞見 1 或收束論證第五段：**

  > **用 Claude Code 要把自己當成 Steve Jobs 或 Jensen Huang。**

  兩人都不是坐下來寫程式的人，但都以**極端精確地講出要什麼、以及不接受「差不多」**
  聞名——Jobs 對細節（連看不到的螺絲、字體）的要求，Huang 對產品方向的堅持。
  這個類比同時打中三個地方：

  - 對到洞見 1：他們的價值不在「會不會打字」，在「講得多精確」。
  - 對到洞見 3／收束論證第四段：他們也以**高標準驗收**聞名，不是做完就放行。
  - 對到收束論證第五段「你本來就是你那件事的專家」：把學員的角色定位成
    「產品/方向決策者」，Claude Code 是執行的工程團隊。

  **會被挑戰的點（先想好怎麼回）：**
  - 「我又不是天才執行長，這樣類比會不會太高調，讓人反而卻步？」
    →要講清楚重點不是「你多厲害」，是「他們的工作方法值得學一招」：
    **精確地說、嚴格地驗**，這兩件事任何人都做得到，跟天不天才無關。
  - 兩人形象兩極（Jobs 已故／Huang 現役、黃仁勳台灣人身分可能引起更強共鳴）——
    面對台灣聽眾，Huang 的例子可能比 Jobs 更有感、更少距離感，可以視現場調整比重
    或只用其中一個。
  - 用真人名人類比有失真風險（他們的實際工作方式是二手轉述，不是第一手查證），
    要當成「好記的比喻」講，不要當成「他們真的是這樣工作」的事實陳述。

  **放的位置建議**：不放進洞見 1 的主段（那裡已經有「翻譯 vs 說清楚」的框架，
  塞名人類比會分散焦點），比較適合放在**收束論證第五段「那你該練什麼」**收尾前，
  一句話帶過當作記憶點：「換句話說，你今天在練的是 Jobs、Huang 那種角色的一小塊——
  講清楚要什麼、驗收對不對，不是他們的名氣或財富。」

  **⭐ 使用者同一時間補的第二句，補上了類比的另一半：**

  > **有很多厲害的部下可以執行你的想法。**

  這句補的不是「說清楚」那一半，是**洞見 2**那一半——Jobs、Huang 能實現宏大想法，
  是因為背後有一整個團隊負責「翻譯成機器聽得懂的話」那一段。**一般人沒有那個團隊，
  所以宏大想法停在想法。** Claude Code 給的不是「變聰明」，是**憑空多出那群部下**——
  這正好對上洞見 2 收在的那句「沒有人會為你一個人寫軟體。以前沒有，以後也不會。
  但現在你可以」。

  兩句合起來，類比其實完整覆蓋了收束論證的三件事框架：
  **知道要什麼 + 確認它真的對**（學員親自做的部分，也是 Jobs/Huang 真正做的部分）
  對上**翻成機器聽得懂的話**（以前要靠一整個團隊，Jobs/Huang 有、一般人沒有；
  現在 Claude Code 讓一般人也「有團隊可用」）。

  **這樣一來位置建議要微調**：這句適合放在**收束論證第二段「被移走的是哪一塊」**
  講完三件事框架、要轉進第三段「所以什麼變了」之前，當一句過渡——
  「Jobs、Huang 從來不缺『很多厲害的部下』替他們翻譯想法。你以前缺，現在也有了。」
  比放在第五段結尾更貼著論證的軸心走，也讓這個類比同時服務洞見 1 和收束論證，
  而不是只當結尾的花絮。

  **⭐ 使用者 2026-08-26 再補一句，把類比從「特定名人」收斂成「一個角色」：**

  > **就像是公司的 CEO，雖然要充分授權，但是規劃、決策、驗收都應該要自己負責。**

  這句其實解決了上面「太高調」那個挑戰點——不用具體點名 Jobs 或 Huang，
  換成「CEO」這個**角色**，任何人都懂「當過主管／被主管交代過事情」是什麼感覺，
  不需要覺得自己要跟名人比。四個詞剛好一一對上論證的既有框架：

  | CEO 的詞 | 對上 |
  | --- | --- |
  | **充分授權** | 洞見 2：把「翻成機器聽得懂的話」那段真的交出去（給 Claude Code 那群「部下」） |
  | **規劃** | 洞見 1／三件事框架第一件：知道要什麼 |
  | **決策** | Lab 過程中持續的取捨與判斷——現有框架裡沒有專門對應的詞，這句補上了這一塊 |
  | **驗收** | 洞見 3／三件事框架第三件：確認它真的對 |

  **最貼的地方，其實是收束論證第四段「誠實的那一半」的第三點「責任不會轉移」**：
  CEO 充分授權出去，出了事還是 CEO 負責，不能說「是部下弄的」——這跟「你沒辦法說
  『是 AI 弄的』」是同一句話換了個場景講。**這句比 Jobs/Huang 的版本更適合放在
  那一段**，而不是收束論證第二段或第五段。

  **建議做法**：兩組類比可以合併使用而不是二選一——
  「Jobs/Huang」負責讓「規劃／驗收」聽起來有份量、好記；「CEO 充分授權」負責把
  「決策」跟「責任不會轉移」補齊，且因為是角色不是真人，**卸掉了「太高調」的疑慮**，
  可以放在誠實限制段直接用，不用像 Jobs/Huang 那句先鋪陳挑戰點才敢用。

### 洞見 2（自動化門檻降到腳邊）

- 補一個台灣在地時薪區間（例如接案時薪 NT$800–1500）跟「20 分鐘做出排程工具」對比，
  比抽象的「兩個禮拜、一筆錢」更有殺傷力。
- 「壞了誰修？」可以再加一句：**維護成本跟開發成本是同一批技能，一起變便宜了**，
  不是「做的時候便宜、修的時候還是貴」。

### 洞見 3（驗證是新的識字能力）

- 具體化「越難收回」的判準，做成一張**三格判斷卡**：能不能 retry？錯了誰看得到？
  成本是秒還是不可逆？比一句格言更容易變成學員回家真的會用的工具。
- 講稿裡直接點名 Lab 2 的紅色 ✗：「還記得剛剛那個紅色 ✗ 嗎？那就是你在做的事，
  只是你不知道它有名字」，把三個 Lab 的體驗串起來，而不只是流程表裡的旁白。
- **⭐ 使用者 2026-08-26 提出：「自己的經驗是要多使用 visualization 的功能」——
  這正好補上洞見 3 現有的一個缺口：講稿說了「你不用看程式碼，你要看行為」，但沒教
  **具體怎麼看行為**。Visualization 就是那個具體做法：**

  - 桌面版本身就有視覺化 diff（CLAUDE.md 選桌面版而非終端機的核心理由之一）——
    這其實已經是這堂課在用的 visualization，只是沒被明講成一個技巧。
  - 可以明講一句可操作的話：**改完東西，先請它截圖或直接打開來看，再決定要不要繼續**，
    不要它「說」做完了就信了。這比「讀程式碼」門檻低得多，非程式背景的人做得到。
  - **把上面的三格判斷卡擴成四格**：能不能 retry？錯了誰看得到？成本是秒還是不可逆？
    **有沒有東西可以親眼看（畫面/截圖/實際跑一次）？** 第四格直接把 visualization
    變成日常判準的一部分，而不是只在洞見 3 講一次就過去。

### 收束論證

- **⭐ 使用者 2026-08-26 提出，值得放進第一段「今天真正發生的事」，把隱含的東西講明：**

  > **除了「解決問題」「做出產品」之外，另外一個目標是幫助自我成長學習。**

  現有第一段只講了兩件事同時成立（沒學會寫程式／做出能用的東西），其實是「解決問題」
  「做出產品」這兩個目標的對照。**第三個目標「自我成長學習」現有講稿其實已經在講，
  只是講到第五段才浮出來**（「練『說清楚』、練『驗證』，在你自己的專業裡練比在程式裡
  練有用」）——這句建議把它**提早明講成第三個目標**，而不是留到第五段才讓聽眾自己拼出來。

  **具體做法**：第一段可以從「兩件事同時成立」改成「三件事同時成立」——
  沒學會寫程式／做出三個能用的東西／**練到一種帶得走的能力**。這樣第五段就不是
  臨時冒出新論點，而是回頭兌現第一段就先承諾的第三件事，論證的收尾會更緊。

  **這樣做的好處，不只是修辭**：現有結構容易被聽成「這堂課 = 教你用一個工具做三個東西」
  （功能導向），补上「自我成長」這個目標之後，變成「這堂課 = 用做三個東西的過程，
  練一種你以後每天都用得到的能力」（能力導向）。後者比較不怕學員回家沒有繼續做小工具
  ——只要「說清楚」「驗證」這兩個能力有練到，這堂課的目標就達成了，不必靠學員持續產出
  才算成功。

  **也直接支援「三、續集構想」第 1 條的回訓場**：如果目標本來就包含「自我成長」，
  回訓場就不是「看誰又做了新東西」的成果發表會，而是「大家在自我成長這條線上走到哪」
  的檢查點，門檻更低、更多人敢來（不用怕自己這個月沒做出新東西就不好意思出席）。

- 第四段「誠實的那一半」加一個具體小故事，把抽象的「80/20 曲線」變成一個聽得懂的畫面
  （例如：把 Lab 1 的記帳工具改成幫全家分帳，前 80% 十分鐘搞定，卡在「四捨五入誰多付
  一塊錢」那個細節花了兩小時）。
- 備用類比再加一個：**數位相機 vs 暗房攝影師**——專業攝影師沒消失，但「隨手拍好照片、
  自稱攝影愛好者」的人多了幾億個。比試算表類比更視覺化，適合口語轉述。

## 三、這堂課之後的續集構想

1. **一個月後的回訓場（成本最低、最推薦）**：回家作業第三題分享會，每人 3 分鐘秀成果 +
   卡住的地方。呼應收束論證結尾「這題只有你做得出來」，順便累積下一場的 Demo 素材庫。
2. **進階場：碰「另一套標準」**——多人協作 repo、串接需要金鑰的外部服務、簡單的資料驗證。
   把誠實限制段第三點（責任不轉移）從警語變成真正教的內容。
3. **10 人這班的社群化**：建一個輕量共享空間，讓大家回家做的「一人份工具」能互相看到，
   延續「一人份工具值得被做」這個論證的生命力。
4. **NTHU 常設課程路線**：問學校有沒有 Anthropic 機構協議、或申請 Claude for Education。
   前置期數週到數月，現在問來得及趕下一輪。見 `provisioning-tokens.md` 的相關段落。

## 四、GitHub 執行細節（block/module ＋ visualization 怎麼落地）

**⭐ 使用者 2026-08-26 提出：「這些訣竅、準則，要如何搭配 GitHub 執行？」**——
上面兩節記的 block/module 逐步驗證跟 visualization，不需要新工具，GitHub 本來就有的
機制剛好能扛。分兩層：這堂課現有結構能直接採用的（零新概念），跟需要新概念、
適合留給續集場的。

### 這堂課可以直接採用（零新概念，只是換節奏）

| 訣竅 | 對應的 GitHub 機制 | 現在 vs 建議改法 |
| --- | --- | --- |
| 一塊一塊做、驗過再做下一塊 | **commit** | 現有 Lab 1 是「做出 v1 → 改一個東西 → 一次 commit」；改成每完成一小塊、看過對了就 commit 一次，不用等整個 Lab 做完 |
| 洞見 3 四格判斷卡第一格「能不能 retry」 | **commit history 本身** | commit 越密，retry 的顆粒度越細——壞掉可以退回上一個「還是對的」的點，不用整個重來。這是那一格的具體實作，可以直接寫進去 |
| visualization／看行為不看程式碼 | **github.com 的 diff 畫面** | 推上去之後，到 github.com 點開那次 commit，看到的就是「改了什麼」的視覺化畫面——跟 Claude Desktop 的本機 diff 是同一個概念，換個地方看。可以在課堂上明講：「推上去之後，回 GitHub 網頁點開這次的 commit，看一眼改了什麼，這也是一種驗證」 |
| 先列出要拆哪幾塊（規劃／CEO 類比裡的「規劃」） | **commit message** | 不用另開工具，commit message 直接寫這一塊做了什麼（例如「加分類功能」「修好四捨五入」）。寫下來的動作本身就是「說清楚」的練習，回頭看 commit 紀錄就是一份「我做了哪幾塊」的清單 |

這一層建議直接採用——不用新增任何步驟或工具，只是把學員已經在做的 commit 動作，
從「一個 Lab 結束才做一次」改成「每個可驗證的小塊完成就做一次」。

### 需要新概念、適合留給續集場（呼應「三、續集構想」#2 進階場）

- **Branch + Pull Request**：一個 block 開一個分支做，做完自己（或找人）review 一次
  diff 再合併回 main。是「一塊一塊做、驗過再合併」的正式版，也是「多人協作 repo」的
  核心機制。
- **GitHub Issues 當 block 清單**：先把「這個東西可以拆成哪幾塊」寫成一張張 Issue，
  做完一塊打勾關掉一個。把 CEO 類比裡「要先規劃」變成一個看得見的產物，不只是嘴上跟
  Claude Code 講。
- **GitHub Actions 做自動化驗證**：每次 push 自動截圖或跑一次檢查，把「親眼看過再放行」
  的視覺化驗證變成自動觸發。Lab 2 已經教過 Actions 的排程用法，這是同一個機制換一個
  觸發時機（`push` 而非 `schedule`）。
