備用案例：GitHub Actions 每日摘要

GitHub Actions 是什麼

GitHub Actions 可以依照指定時間，在 GitHub 的雲端環境執行工作。

執行時間與內容寫在 workflow 檔案中，因此你的電腦關機時排程仍可執行。

步驟 1建立 workflow
貼給 Claude Code
我要一個每天自動執行的功能，請用 GitHub Actions 做：
1. 每天台灣時間早上 6 點自動執行
2. 抓 Google 新聞的 RSS（繁體中文台灣版），取前 5 則標題和連結
3. 存成 digest/YYYY-MM-DD.md 這樣的檔案，然後自動 commit 回這個 repo

要求：
- 一定要能手動按按鈕執行（workflow_dispatch），我今天上課就要看到結果
- workflow 要有 contents: write 權限，不然推不回來
- 不要用任何 npm 套件，用 Node 內建的功能就好

做好之後把檔案 push 上去。

為什麼要列出這三項要求？

它們分別處理手動測試、寫入權限與套件相依性，是這個題目常見的失敗原因。在需求中先列出限制，可以減少後續修正。

步驟 2手動執行 workflow

⚠️ 檔案一定要先 push 上 GitHub，這一步才有東西可看。存在自己電腦裡不算。

  1. 打開你的 repo → 點上面的 Actions 分頁
  2. 左邊點你的 workflow（大概叫 Daily Digest）
  3. 右邊按 Run workflow → 再按一次綠色的 Run workflow

你會看到：🟡 黃色轉圈圈 → 大約 30 秒 → ✅ 綠色打勾。

步驟 3看成果

回 repo 首頁按 F5，會多出一個 digest/今天日期.md，點進去是今天的新聞標題。

檔案由 GitHub Actions 產生

workflow 會把檔案寫入 repo，並在每天早上 6 點再次執行。

展示與回顧

課程成果是一個可操作版本，以及一套可以再次使用的專題流程。

專題流程

提出問題 → 定義目標 → 拆解計畫 → 分段實作 → 驗證 → 決定下一步

① 尚未釐清的需求無法完整交給 AI

如果經過幾次修改才符合需求，通常表示最初有些條件尚未說明。

例如中文介面、刪除功能與手機版面，對你而言可能理所當然，但 AI 不會自行知道。

產生程式碼的成本降低後，釐清需求與做出取捨變得更重要。

② 計畫可以依實作結果更新

計畫代表目前的理解。看到第一版後發現新的限制，可以先更新目標與步驟，再進行下一輪。

調整計畫是專題的一部分，不代表前面的規劃失效。

③ 每一步都需要可操作的驗收方式

明顯不符合需求的結果容易發現；更需要注意的是外觀看似正確、實際行為卻不正確的結果。AI 的語氣可能很確定，但輸出仍需要驗證。

所以新的能力不是讀得懂程式碼，是在它動手之前，你先說得出「做好了應該長什麼樣」。今天每一段的 ✅ 檢查點，練的就是這件事。

調整顏色等可回復的修改，可以先執行再檢查。刪除資料、寄送訊息或產生費用前，應先確認內容與影響。

驗收前問四件事：能不能回上一版？做好該看到什麼？錯了誰會看到、影響是什麼？有沒有畫面、截圖或實際執行結果可以親眼看？

使用限制

使用時需要注意：

  • 最後一部分通常最花時間。 課堂題目已控制範圍；自行製作其他工具時，細節可能需要較多時間。
  • 責任不會轉移。 可以把執行工作交給 Claude Code，但規劃、決策與驗收仍由使用者負責。
  • 個人使用與提供他人使用，需要不同標準。 涉及金錢或個人資料時，需要增加安全、測試與資料處理措施。
  • 完成這堂課不等於具備所有軟體開發能力。 本課程練習的是需求描述與驗證。

後續練習重點

描述需求：把隱含條件、限制與預期結果寫出來。

驗證結果：動手之前先定義「做好了應該長什麼樣」。

請在自己熟悉的工作領域練習這兩項能力，因為你最了解該領域的需求與判斷標準。

操作原則

  • 結果不符合需求時，補充條件後再修改
  • Claude Code 詢問權限時，先確認操作內容
  • 處理時間較長時，查看正在修改的檔案
  • 把功能、結果與限制寫完整
  • 保留完整錯誤訊息，作為修正依據

GitHub 名詞對照

  • repo — 會記得所有版本的資料夾
  • commit — 存檔，並寫一句改了什麼
  • push — 把存檔上傳到 GitHub
  • Actions — 雲端電腦，可按時自動做事
  • Pages — 把網頁變成公開網址

  2. 從「這次不做」選一項，加入下一版計畫
  3. 完成一個步驟、測試並保存版本
